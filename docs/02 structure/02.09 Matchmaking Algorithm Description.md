# G1.1 - MatchMaking Design Specification
## Owner: Platform Core Sub-team
## Sub-Team: Platform Core
## Iteration: 1

---

# Purpose

"MatchMaking" is responsible for managing matchmaking queues and producing skill-based player pairings for supported game types.

It serves to:
- Maintain per-game matchmaking queues
- Add/remove players from queues
- Support party-based queueing
- Perform skill-based pairing using rank/MMR-derived values
- Return matched player groups for downstream room/session creation

"PartySystem" supports pre-match player grouping so that players can queue together and be matched as a unit.

---

# Design

- Support for multiple game types
- Keep matchmaking logic separate from UI and game engine logic
- Use skill-based matching
- Support party queueing
- Provide queue inspection helpers (queue size / position / in-queue checks)

---

# Core Responsibilities

## Queue Lifecycle

- Maintain a matchmaking queue per game type
- Enqueue players (or parties) for a selected game type
- Prevent duplicate queue entries
- Remove players who leave queue before a match is found
- Expose queue position lookup for a player
- Expose queue size lookup per game type
- Expose "is player currently queued" checks

## Skill-Based Matching Pipeline

For each matchmaking pass:
- Read eligible queued players/parties for a game type
- Resolve skill values for candidates
- Apply compatibility checks (same game type, etc)
- Expand acceptable skill gap as wait time increases (Could be a later iteration thing)
- Remove matched players/groups from queue
- Return matched groups to the caller for room/session handoff

## Party Queue Support

- Create and manage parties before queueing
- Allow players to join/leave parties
- Queue a party as a single matchmaking unit
- Prevent splitting party members across different matches
- Validate that party size fits the target game type

# Algorithm Description

## Current Implemented Baseline

The current MatchMaking Java boilerplate implements a basic matcher:
- Players are queued by gameType
- Duplicate queue entries are prevented by PlayerQueue.enqueue(...)
- matchPlayers(gameType) returns the first two queued players (if available)
- Skill-based rank/MMR matching is needed to be done in future iteration

---

## Target Algorithm Design (Skill-Based Matchmaking)

### High-Level Strategy

For a selected gameType, the algorithm:
1. Reads eligible queued players (and later, party queue entries)
2. Resolves a numeric skill value for each candidate (MMR preferred)
3. Scans candidates in queue order (oldest first)
4. Selects an anchor player/group
5. Searches for compatible opponents within a skill tolerance
6. Forms a match when required player count is reached
7. Removes matched entries from the queue

This aligns with the Platform Core design where MatchMaking finds pairings and downstream services handle room/session creation and notifications.

---

## Inputs and Outputs

### Inputs
- gameType: String
- Matching queue for that game type (PlayerQueue)
- Queued players (and later party entries)
- Skill values for queued players (MMR/rank-derived/default)

### Output
- A list of matched player IDs for the game type

---

## Compatibility Rules (Iteration 1 Design)

A candidate is compatible with an anchor if:
- Both are queued for the same gameType
- Candidate is not already selected in the current matchmaking pass
- Candidate is not the same player/party as the anchor
- Adding the candidate does not exceed the match size
- Skill gap is within the current allowed threshold

### Skill Value Resolution (Design)
MatchMaking compares players using a numeric skill value:
1. rank/MMR
2. Default value (new player / no stats)

---

## Wait-Time Tolerance Expansion (Refinement Policy)

To balance fairness and queue times, the allowed skill gap may expand as players wait longer.

### Example
- Base tolerance: 100 MMR
- Increase: +50 MMR every 15 seconds waited
- Maximum tolerance cap: 400 MMR

So we will start with stricter matches but will become less strict as time goes on

---

## Core Matching Flow (Step-by-Step)

### On Enqueue (addPlayerToQueue)
1. Validate gameType
2. Reject duplicate queue entries
3. Enqueue player into the PlayerQueue for that game type

### On Matchmaking Pass (matchPlayers)
1. Check whether enough players are queued
2. Read queue candidates
3. Resolve skill values for candidates
4. Attempt to build a valid match using compatibility checks
5. If a match is found, remove matched players from queue
6. Return matched players to caller

### On Leave Queue (removePlayer)
1. Search active queues for the player
2. Remove player if found
3. Return control to PlatformCore/UI flow

---

## Party Queue Support (Design vs Current Boilerplate)

### Currently implemented
- Party creation, joining, leaving, and disbanding are implemented in PartySystem
- Party stores host, members, and max size

### Planned matchmaking integration
- Queue a party as a single matchmaking unit
- Prevent splitting party members across different matches
- Validate party size against target game type
- Use party-level skill value (e.g., average member MMR/rank)
