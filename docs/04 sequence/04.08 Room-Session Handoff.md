## Owner: Platform Core Sub-team
## Sub-Team: Platform Core
## Iteration: 1

---
# Purpose
The Room Manager is responsible for managing the lobby lifecycle until gameplay begins.
It serves to:
- Create a room with the specified host, game type, and max players.
- Track players in a lobby
- Enforce capacity limits
- Determine when a room is ready
- Lock the room before gameplay
- Provide session initialization data to the session layer
- The Room system does not create or manage game sessions.
- Session creation is handled by GameSessionManager.

The GameSessionManager is responsible for:
- Validating the parameter given from the room
- Creating the session
- Initializing the game state

# Design
- Keep lobby logic separate from gameplay logic
- Do not embed session logic inside Room classes
- Use RoomStatus to represent the lifecycle
- Expose only the data required to start a session
- Make handoff simple and stateless
- Prevent players from joining after session starts

# Core Responsibilities
This contract is responsible for the safe and seamless transition of players from the waiting room to the game. It ensures that the lifecycles of a room and session are unidirectional, meaning that player will not be able to join once the statuses of the room and session are set to IN_PROGRESS. The contract also ensures that the room, once validated, gives the session layer the necessary parameters that will seed the GameState and allow the game to begin. 
# Room Lifecycle

RoomManager manages:
- Room creation
- Player joins
- Player leaves
- Capacity enforcement
- Room cleanup

# Handoff Preparation
When a room becomes ready, RoomManager must:
- Mark the room as FULL
- Lock room by changing its status to IN_PROGRESS
- Block players from joining once the status is modified

It must provide the following to the session layer:
- roomId
- gameType
- playerIds as a List

After this, the session layer takes over and the RoomManager’s responsibility ends.

# Post-Handoff Session Layer Action
Once the session-layer is given parameters from the room, it must do checks to ensure that:
- The engineRegistry contains the desired engine for the given gameType
- There are at least two players entering the session
- Players must have unique IDs

Should any of these conditions be broken, the session will return a corresponding error.

Otherwise, the session layer will proceed by:
- Creating a new session with a distinct sessionId
- Initialize a GameState with:
  - A new game board
  - Player order with the turn index set to the first player
  - An IN_PROGRESS status
  - Empty move history
- The GameSession status will also be set to IN_PROGRESS
- The start time is recorded
- And the unique session ID is stored

# Room Lifecycle States
OPEN >> accepting players
FULL >> capacity reached, ready for session
IN_PROGRESS >> locked, gameplay active, joins blocked
CLOSED >> finished or empty, removed from manager

Players join → Room becomes FULL → RoomManager locks room (IN_PROGRESS) → Room data passed to GameSessionManager → Session created

# Parameters passed
- roomId
- GameType
- playerIds
